# Async specification (§15)

## Scope and coverage

Spec §15 and the related edits from `abf7aff` (`docs/spec.md` and the "Async
support" milestone in `agents/todo.md`), reviewed by three independent reviewers.
Each reviewer covered one lens:

- **Semantics:** consistency with §3–§10, ambiguity, static checking.
- **Runtime:** implementability on LuaJIT in this codebase. This reviewer
  prototyped the cancellation model in Lua and measured its cost. The
  prototype is in `agents/prototypes/async/runtime/`.
- **Usage:** realistic programs written against §15 (a TCP server, a fan-out
  client, a pipeline, retry, cleanup, and a test), compared with asyncio and
  Trio. The programs are in `agents/prototypes/async/programs/`.

Line numbers refer to `docs/spec.md` at `abf7aff`.

## Summary

The structured-concurrency core is sound and maps cleanly onto the existing
runtime. Lua coroutines hold whole task stacks, and LuaJIT yields across
`xpcall`, so awaiting a coroutine can be a plain call inside the task, with no
state-machine transform. Cancellation reuses the generator `__wlo_cancel`
sentinel and `__wlo_try`'s `"cancel"` path. Origin and protection rules reduce
to a flag on each group, a parent pointer, and saving and restoring the task's
scope around `finally`. A prototype passed every scenario `todo.md` asks for. To run it, use
`../../../vendor/luajit/src/luajit scenarios.lua` from
`agents/prototypes/async/runtime`. Costs on Linux (arm64 container) and on
macOS (arm64, native):

| Measurement | Linux | macOS |
| --- | --- | --- |
| resume and yield | 13 ns | 12 ns |
| Protection overhead per `try` | about 14 ns | about 15 ns |
| Memory per suspended task | 0.74 KB | 0.74 KB |
| Start, sleep, and join 100k tasks | 0.24 s | 0.17 s |
| Cancel and join 100k suspended tasks | 0.25 s | 1.6 s |
| `error` caught by `pcall` (`errbench.lua`) | about 1 µs | about 15.5 µs |

Cancellation unwinds each task with `error`, and LuaJIT on macOS arm64 unwinds
errors through the system unwinder. Cancelling a task therefore costs about
16 µs on macOS, linear in the number of tasks. That is negligible for the first
workload. The same per-raise cost already applies to Willow exceptions on
macOS.

The problems are in four places:

1. **Where checkpoints sit.** The spec doesn't say exactly when cancellation is
   delivered, and the plausible readings disagree on whether resources leak and
   whether `except` runs.
2. **The static rule for group exits.** As worded, it permits an unsound
   checker. It also over-rejects code inside `finally`, and rejects the most
   common fan-out pattern.
3. **The library.** Nothing in §15 can suspend except a join, and nothing can be
   bounded by a timeout. No real workload can be written yet.
4. **Small gaps.** Async protocol methods, async tests, states, messages, and
   the reserved name `Task` all need a decision.

On every open question that more than one reviewer answered, they agreed.

## Findings

### 1. High: checkpoint placement is unspecified (2175–2176, 2226–2232, 2298–2304, 2367–2375)

"An await is a cancellation checkpoint" doesn't say whether delivery happens
before the operand is consumed or after its result is produced. Both readings
are wrong for some program:

- **Before:** `await serve(conn)`, where `serve` enters `with conn:` first,
  never runs, so the connection leaks. The handoff pattern in 2367–2372 then
  fails.
- **After:** `conn = await open_connection()` acquires the resource and then
  drops it.

A related problem: when a child fails, it finishes its task and also requests
cancellation of the body. `await t` inside `try`/`except` may then either run
the handler or skip it (2230–2232). That difference is observable.

**Recommendation** (runtime findings 1–2 and semantics findings 2–4, which
agree):

- Awaiting a coroutine is not a checkpoint. It always enters the body, and
  delivery happens at checkpoints inside it, as for an admitted task.
- Checkpoints are:
  - async native operations, checked before they act and again after waking;
  - awaiting a task, where a pending unprotected request is delivered before
    the task's outcome even if that outcome is ready;
  - group-exit boundaries.
- Leaving a protected `finally` is not a checkpoint. A pending request waits for
  the next one, so no checkpoint is hidden from the checker.
- A request stays in effect for every task in the requesting group until that
  group exits. Each unprotected checkpoint delivers it again. Raising and
  catching an exception during cleanup cannot clear it.

### 2. High: the static rule across groups is imprecise (2342–2358)

"Can also be a checkpoint" and "before the first checkpoint" don't say which
points are exits.

- **Unsound:** in the following program, a checker that skips the inner join
  accepts `print(x)` with `x` unassigned. The inner group cannot absorb the
  outer stop, so `x = 1` is skipped.
  ```python
  async with aio.task_group() as outer:
      outer.start(stopper(outer))
      async with aio.task_group() as inner:
          inner.start(slow())
      x = 1
  print(x)
  ```
- **Over-rejects** (semantics finding 1): an assignment at the end of a
  `finally` inside the body always runs, because that `finally` is protected,
  yet the text treats it as skippable.
- **Over-rejects** (usage finding 3): in
  `task = group.start(fetch(h)); data = await task; return data`, nothing can
  stop the group by its own request. Outer requests aren't absorbed, and
  failures leave by exception. The spec still reports a missing return and a
  possibly unassigned `data`, which makes users add a dummy `raise` or a
  `None` pre-assignment.

**Recommendation:**

- Specify each `await` and each nested `async with` exit as a possible implicit
  transfer, like `break`, to the end of every enclosing `async with` in the
  same function that isn't separated from it by a `finally`. This reuses the
  existing `break` and `finally` checker machinery (`check.lua:1324-1335`).
  The runtime reviewer's checker sketch is the same idea: snapshots at the
  same `finally_depth`.
- Add usage's pruning rule: a group whose `as` name is used only as the
  receiver of `.start(...)`, or that has no `as` name, has no graceful exits.
  §15's own example and the fan-out pattern then type-check.

### 3. High: no suspension, sleep, or timeout (1565–1573, 2174–2177, 2319–2321)

`aio` contains only `task_group`.

- **No suspension:** a loop of `await step()` that never touches I/O starves
  its siblings. `time.sleep` compiles and blocks every task.
- **No bounds:** nothing can bound an await or a join. Protected cleanup such as
  `finally: await conn.sendall(...)` to a stalled peer hangs a graceful
  shutdown forever.
- **Watchdogs don't help:** a watchdog child holds its group open for the full
  deadline.

**Recommendation:** this answers the "first useful workload" question. All three
reviewers converged on a TCP echo server on loopback, with:

- one task per connection;
- per-operation timeouts;
- a drain on a client command;
- an async test that drives it.

The minimal surface uses `net`'s validation and messages:

```text
sleep(seconds: float) -> Coroutine[None]      # sleep(0) always yields
listen(host: str, port: int, backlog: int = 16) -> Listener
connect(host: str, port: int, timeout: float | None = 30.0) -> Coroutine[Connection]
Listener.accept(timeout: float | None = None) -> Coroutine[Connection]
Connection.recv(size: int, timeout: float | None = None) -> Coroutine[bytes]
Connection.sendall(data: bytes, timeout: float | None = None) -> Coroutine[None]
close / enter / exit stay synchronous, so plain `with` works
```

Use numeric hosts, or document that name resolution blocks the loop. Leave out:

- HTTP, which needs `curl_multi` because `curl_easy_perform` blocks and its FFI
  callbacks cannot yield;
- processes;
- files.

`aio.task_group(timeout=...)`, which raises `TimeoutError` at the boundary, can
follow next. It exits by exception, so it adds no normal exits for the checker.

### 4. Medium: deadlock and self-await are unspecified (2213–2232; runtime 5, usage 4)

When a task awaits its own handle, or two tasks await each other, the loop has
no ready tasks, no I/O, and no timers, and `poll` blocks forever.

**Recommendation:** add to §10, "Failures that are not exceptions": "if no task
can run and no I/O or timer wait is pending, the program reports
`deadlock: all tasks are waiting` and exits 1". The check is one line in the
loop.

### 5. Medium: outer request vs inner admission (2269–2270; runtime 3)

If an outer request stops admission into an inner group, a `group.start(...)` in
protected cleanup raises `RuntimeError`, and a graceful shutdown exits by
exception.

**Recommendation:** admission depends only on the group's own stop or failure.

### 6. Medium: awaiting a sibling in cleanup crashes a graceful stop (2230, 2272–2275; usage 5)

Under `finally: await background`, where the same `group.cancel()` cancelled
`background`, the await raises `RuntimeError`. That error becomes the body's
failure, and the group exits by exception instead of absorbing its stop.
Python users write exactly this.

**Recommendation:** awaiting a task cancelled by a stop of a group that also
encloses the awaiter completes the await as that same stop. If that is too
subtle, at least give the error a clear message.

### 7. Medium: async protocol methods and async tests (167–170, 271–298, 1510–1515)

- **Protocols:** they don't say whether `async def` may appear in a `protocol`,
  or whether `async def recv(self) -> bytes` and
  `def recv(self) -> Coroutine[bytes]` satisfy each other. Allow it as exact
  sugar for the `Coroutine[T]` return.
- **Tests:** `async def test_x() -> None` arguably satisfies "return `None`".
  A runner that drops the coroutine would report PASS without running the
  body. All three reviewers recommend running `async def test_*` as the root
  task of its process, like async `main`. Failing that, reject it as a check
  error.

### 8. Low: wording and smaller gaps

- **States:** "active", "inactive", "stopping", "joining", and "exited" are used
  but never defined (2248, 2270, 2279–2280). Define inactive → active → exited,
  with "stopping" meaning active with a stop requested. `cancel` is valid while
  active, and `start` while active and not stopping.
- **Line 2283** can be parsed two ways ("unless it has recorded a failure or
  cancellation from an outer group remains pending"). Split it into two
  conditions.
- **Messages:** none of the new `RuntimeError`s has an exact message. Usage
  suggests `coroutine was already awaited or started` and
  `awaited task was cancelled`.
- **Definitions:** "cancelled task" is undefined. Define it as a task whose body
  was exited by cancellation unwinding.
- **Rejected `start`:** say that a rejected `start` does not consume its
  argument.
- **Discard rule:** the rule at 975–976 conflicts with checking generic bodies
  "for every permitted type argument" (255–256). Exempt type parameters and
  cover unions containing `Coroutine`.
- **`await` precedence:** the operand level isn't stated (`await await c`,
  `await -x`).
- **Unusable union:** `Coroutine[T] | Task[T]` is valid but can't be used.
  Restrict these types to `X | None`, or allow them in `isinstance`.
- **Reserved name:** reserving `Task` breaks ordinary `class Task:` programs.
  Use `aio.Task[T]` instead.
- **Spec content:** 2379, about fd reuse, is an implementation requirement. The
  observable rule is "an operation never acts on another handle". The runtime
  must check `closed` after every wake.
- **`exit(None)` on cancellation** (2295, 1083–1085): §8 should say that `None`
  also means "interrupted", or `atomic_writer`-style managers commit truncated
  output.
- **Concurrent waits:** allow one pending wait per handle per direction, and
  raise `RuntimeError` for a second one. Otherwise concurrent `sendall` calls
  interleave.
- **Preference, not a defect:** `Coroutine` and `Task` could be covariant.

## Open questions in `agents/todo.md`

- **Outer cancellation and inner failure:**
  1. The inner group joins all its children.
  2. It propagates its failure as an exception.
  3. The outer request is not consumed. It is a flag re-read at every
     checkpoint, and is delivered at the next unprotected one.
  4. At the requesting group's boundary, an uncaught failure beats absorption.
     If code caught it, the stop is absorbed.

  No exceptions are aggregated, and no request is lost. The runtime prototype
  exercised exactly this. Replace 2337–2340 with it.
- **Scheduling:**
  - Use a FIFO ready queue.
  - Keep "need not suspend" for ready results, subject to finding 1.
  - Make `await aio.sleep(0)` the yield operation, with no separate `yield_now`.
  - Use `poll()` with a timer heap. A sorted timer list could not handle 100k
    sleepers.
- **Async tests:** see finding 7.
- **Tracebacks:**
  - Frames stop at the task root, then add one line,
    `in task started at file:line:col`.
  - Re-observing a failure through `await`, `result()`, or the group re-raises
    it unchanged with `error(err, 0)`. The `__wlo_generator_raise` pattern would
    append frames on every observation.
- **Cancellation representation:** one sentinel shared with generators. Each
  group has a `cancelled` flag and a `parent` pointer, and each task has a
  `scope` that is set to `nil` while protected. On `cancel`, scan the suspended
  tasks and wake those that now see a request. Give each wait an id so stale
  wakes are ignored.
- **Compiler control flow:**
  - Emit `async def` like a generator (`emit.lua:341-362`).
  - `await` is a helper call.
  - `async with` reuses `lower_with`'s `Try` node with a
    `__wlo_group_exit(m, code, value)` finally that can absorb or convert a
    departure. Plain `with` stays non-suppressing.
- **Resource ownership:**
  - Check before acting.
  - The wait primitive returns "cancelled" or "closed" so `connect` can close
    its socket before unwinding.
  - Mark a connection broken before suspending a partial send.
  - Groups keep only their unfinished children, and handles keep their own
    outcomes.

## Recommended order

1. Edit §15 to settle checkpoint placement, persistent requests, and
   protection exit (finding 1), and the outer/inner rule above.
2. Restate the static rule as implicit transfers, with the pruning rule
   (finding 2).
3. Settle the small semantic points: admission (5), deadlock (4), group states,
   messages, the `Task` name, async protocol methods, and async tests (7–8).
4. Specify the `aio` surface for the TCP echo server (finding 3), then plan the
   implementation slices from the runtime notes above.

## Outcome

The decisions are recorded in spec §15 and in `aio` in §14, and the
implementation slices are in the async milestone in `agents/todo.md`. They
adopt the recommendations above, with these differences:

- **No pruning rule.** The static rule has no exemption for groups that
  nothing can stop by their own request. §15 shows the idiom instead: start
  tasks in the group, and read their results after it.
- **Awaiting a cancelled task.** It raises `RuntimeError` with the message
  `task was cancelled`, even in cleanup.
- **Overlapping operations.** The limit applies to unfinished operations per
  direction, not to pending waits, because `sendall` sends before it first
  waits.
- **First surface.** It includes `aio.connect` and `Listener.local_port()`.
  Async TCP inherits `net`'s semantics.
