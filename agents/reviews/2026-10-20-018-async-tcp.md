## F1. Closing an `aio.Listener` outside the event loop crashes

Medium · Correctness · Fixed · `runtime/aio.lua:23`, `runtime/aio.lua:54`

`aio.listen` and `Listener.close` are synchronous, so a synchronous function
may call them before or without an event loop, for example in a synchronous
`main` or a synchronous test. `__wlo_aio_listener_close` calls
`__wlo_aio_wake_fd`, which iterates `__wlo_aio_fd_waits`. That table is
assigned only in `__wlo_aio_run`, so outside the loop it is `nil` and
`ipairs` raises an internal Lua error. The listener's descriptor is closed
first, but the program ends with a runtime error. A `with` statement fails the
same way through `exit`.

### Evidence

```python
import aio

def main() -> None:
    listener = aio.listen("127.0.0.1", 0)
    print(listener.local_port() > 0)
    listener.close()
    print("closed")
```

prints `True`, then
`sync_listen.wlo:6:14: error: bad argument #1 to 'ipairs' (table expected, got nil)`
and exits with status 1. `with aio.listen("127.0.0.1", 0) as listener:` in a
synchronous `main` reports the same error at the `with`.

### Fix

`runtime/aio.lua` creates `__wlo_aio_fd_waits` as an empty table when the
module loads, so `__wlo_aio_wake_fd` finds no waits when a handle closes
outside the loop; `__wlo_aio_run` still resets it.
`tests/programs/aio_listener_outside_loop.wlo` opens and closes listeners from
a synchronous `main`, directly and with `with`; it fails without the fix.

## F2. The cancelled-connect test depends on the host's network routes

Low · Testing · Fixed · `tests/unit/aio_test.lua:696`

`aio_cancelled_connect_closes_its_socket` needs a connect that stays pending,
and gets one by connecting to `10.255.255.1:80`. That works only when the
host routes the address to a gateway that drops it. On a machine with no
route to it, such as one that is offline or a container without networking,
`connect(2)` fails at once with `ENETUNREACH`; on a network where the address
answers, it is refused or connects. The task then fails with `OSError` or
completes, and the test fails although the runtime is correct.

### Evidence

`route -n get 10.255.255.1` on the review machine shows the address leaving
through the default gateway `10.0.0.1`; the test passes only because of that
route. A loopback listener gives the same pending connect without the
network: a scratch program listening with `backlog=1` and never accepting saw
the first `aio.connect` succeed and the next four each time out after 0.3
seconds, so those connects stayed pending.

### Fix

The test listens on 127.0.0.1 with a backlog of 1 and never accepts, starts
eight connects, and requires at least one to be pending after 50 ms; once the
backlog is full, further connects stay pending on both macOS and Linux. After
the group is cancelled, the test closes the connections that completed and
checks that the descriptor count is back where it started. It passes on macOS
and in a Linux container with no network.

## F3. No test has a `recv` and a `sendall` waiting at the same time

Low · Testing · Fixed · `tests/unit/aio_test.lua:618`

Spec §14 lets a `recv` and a `sendall` run at the same time on one
connection. Both then wait on one descriptor, which the scheduler polls
through a single pollfd with the two waits' events combined, and each wait
must wake only for its own readiness. The plan's test plan lists "`recv` and
`sendall` together", but `aio_one_operation_per_direction` sends two bytes
while the `recv` is pending, and that `sendall` finishes without waiting. No
test has both directions suspended at once, so a regression in how the shared
pollfd's events are combined or dispatched would go unnoticed, as a hang or a
lost wake.

### Evidence

The behavior is correct. A scratch program started an 8 MiB `sendall` and a
`recv` on one server connection, sent `hi` from the client, then started a
task draining the client. It printed `reader got hi`, `before drain`,
`writer done`, and `drained 8388608` in that order: the reader woke on its
data while the writer stayed suspended, and the writer woke once the client
drained. Closing the server while both were suspended made both raise
`I/O operation on closed connection`.

### Fix

The unit test `aio_recv_and_sendall_wait_at_the_same_time` blocks a 16 MiB
`sendall` on a full buffer while a `recv` waits on the same connection. Data
from the peer wakes the `recv` while the send stays blocked, and the send
finishes once the peer drains it.

  received their own data.
- Two `accept`s on one listener: the second raised
  `accept is already in progress`, and the listener accepted afterwards.
- Cancelling a group with a pending `recv` and a pending `accept`: the
  connection then received data and the listener accepted again.
- A synchronous `main` closing an `aio.Listener`, directly and through `with`
  (F1).
- A full-backlog loopback listener kept later `aio.connect`s pending until
  their timeouts (F2).

## Verdict

The TCP handles match `net`'s validation, messages, timeouts, and unusable
state. Each direction allows one operation, and checkpoints run before acting
and after every wake. `close` wakes pending operations through their own wait
ids, so stale wakes and reused descriptors are ignored, and cancelled connects
and partial sends release or mark what they hold. Bundling keeps host.lua out
of programs that only sleep or use groups. F1, a crash when a listener was
closed outside the event loop, is fixed; F2 and F3 make the cancelled-connect
test independent of the network and cover a `recv` and a `sendall` waiting at
once.
