## F1. A key that calls is checked after the arguments it precedes

Medium · Correctness · Fixed · `compiler/check.lua:805`, `compiler/check.lua:940`

Both argument loops skipped every key and checked it after the other
arguments, but lowering evaluates arguments in the order they were written. A
key such as `mk()` contains a call, and per §9 a call removes the narrowing of
captured variables. Checked last, the call came too late: in
`sorted(xs, key=mk(), reverse=flag)`, `reverse` was still narrowed to `bool`
even though `mk()` runs first and may set `flag` to `None`. The program then
type-checked and sorted with `reverse` set to `None`.

### Evidence

A scratch program with `flag: bool | None = True`, a closure `mk` that
assigns `flag = None` through `nonlocal`, and
`sorted([1], key=mk(), reverse=flag)` type-checked and ran.

### Fix

Only a lambda or built-in function value key is deferred (`deferred_key`).
Both take their parameter types from the items, and creating either calls
nothing, the same reason `infer_call` defers lambdas. Every other key is
checked in evaluation order with no expected type, and `check_sort_key` uses
the type it recorded. A unit test covers the example above.

## F2. Key diagnostics name a `None` result the user never wrote

Low · Error handling · Fixed · `compiler/check.lua:716`

`check_sort_key` checked every key against `(item) -> None`, using `None` as a
placeholder for the result. Two diagnostics exposed it:

- `xs.sort(key=lambda a, b: a)` reported
  `expected (int) -> None, received a lambda with 2 parameters`.
- A generic function key such as `key=ident` reported
  `cannot infer type parameter 'T' of 'ident' from int and None`.

### Fix

A lambda key with other than one parameter reports
`a sort key takes 1 parameter, received a lambda with 2 parameters`. A
function value key is no longer given the placeholder (see F1), so a generic
one reports the existing
`generic function 'ident' needs type arguments or an expected callable type`,
as a generic function argument to a generic call does. A unit test covers the
lambda message.

## Checks run

- Scratch programs sorted with a callable variable, `float`, `str`, `len`,
  lambdas over a list, a dictionary, and a `range`, `reverse` with a key, an
  explicit `key=None`, and `ident[int]`; each printed the expected order.
- A key that sorts its own list in place raised `list changed during sort`.
- `key=print`, an optional callable variable, and duplicate `key` arguments
  each reported one diagnostic.
- `make test` after the fixes: 336 passed, 0 failed.

## Verdict

The keys, run-time ordering, change detection, and failure behavior match
spec §7. F1 was a narrowing soundness gap in how keys were checked, and F2 a
pair of misleading diagnostics; both are fixed with regression tests.
