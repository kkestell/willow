# Sort keys

## Goal

Finish the sorting milestone (spec §7 Lists and dictionaries):

- `sorted(items, reverse=False, *, key=None)` and
  `xs.sort(reverse=False, *, key=None)` take a keyword-only `key`: a callable
  taking one `T` and returning `int`, `float`, `str`, or a comparable tuple.
  With a key, elements may have any type.
- The key is evaluated exactly once per element, in input order, before any
  reordering (`sorted` consumes its iterable first). Elements with equal keys
  keep their order in either direction.
- A key that changes the list being sorted in place raises `RuntimeError`
  `list changed during sort`. Key failures, NaN keys, and that error leave
  the input in its original order.
- `report.wlo` orders levels by a count-then-name key instead of its `by_count`
  grouping, and the Rosetta Code "Sort using a custom comparator" example
  sorts by descending length, then case-insensitive text.

## Related code

- `compiler/stdlib.lua`: the `sorted` built-in signature.
- `compiler/check.lua`: `builtin_params` (no keyword-only support yet),
  `SORT_PARAMS`, `check_sortable`, the built-in `Call` argument loop and its
  `sorted` branch, `check_method`'s `list.sort` path, and the `Lambda` branch,
  whose `infer_result` takes the result from the body.
- `compiler/lower.lua`: built-in calls, the `sort_items` path for non-list
  iterables, and `list.sort` lowering through the `list_sort` helper.
- `runtime/core.lua`: `__wlo_sorted_values`, `__wlo_sorted`, `__wlo_list_sort`,
  `__wlo_sort_items`, `__wlo_has_nan`.

## Decisions

- **Signatures.** `builtin_params` reads an optional `keyword_only` table, and
  `sorted` declares `key` as parameter 3, keyword-only, defaulting to `None`.
  `SORT_PARAMS` gains the same `key`.
- **Checking a key** (`check_key(arg, item, state)`), shared by both:
  - a `None` literal means no key;
  - a lambda gets the expected type `(item) -> None` with `infer_result`, so
    its body gives the result; a built-in function value gets
    `(item) -> <its declared result>`; other values are checked as they are;
  - the key's result is the callable's result (or the function's return type),
    which must be ordered (`types.ordered(r, r)`), or the call reports
    "cannot sort by a key of type R";
  - the argument is then expected to be `(item) -> R`, which gives the usual
    "expected ..., received ..." message for a wrong parameter, and lets
    lowering adapt functions and floats.
  The argument loops skip the key, which is checked after `items` and
  `reverse`; checking a key calls nothing. Without a key, the elements must be
  sortable as before; with one, any element type is allowed.
- **Run time.** `__wlo_sorted_values(list, reverse, key, site)`:
  - with a key, copies the elements, evaluates every key in input order, and
    for an in-place sort then checks that the list kept its length and
    elements, or raises `list changed during sort`;
  - checks keys (or elements) for NaN;
  - orders positions by key, with ties in input order;
  - returns the reordered elements. Callers write them back only after all of
    this succeeds, so a failure never reorders.
  `sorted`, `list_sort`, and `sort_items` pass `key` through; `list_sort` asks
  for the change check.

## Test plan

- `tests/unit/check_test.lua`:
  - `sorted([[1]], key=lambda x: len(x))` and `xs.sort(key=len)` on a
    `list[str]` type-check; the result of `sorted` with a key is a list of the
    elements;
  - `key=lambda x: [x]` reports "cannot sort by a key of type list[int]";
  - `sorted([1], lambda x: x)` reports a positional argument for the
    keyword-only `key`;
  - a key function taking `str` for `int` elements reports the expected
    callable type;
  - `sorted([[1]])` without a key still reports "cannot sort".
- `tests/programs/sort_keys.wlo` and `.out`:
  - records sorted by a field, by a tuple key, reversed with ties kept in
    input order, and by a bound method and a named function;
  - `sorted` over a generator with a key that logs, showing all items consumed
    and each key evaluated once, in input order;
  - `list.sort` with a key that appends to the list raises
    `list changed during sort`, and the list keeps its order;
  - a key raising `ValueError` part way, and a NaN key, both leaving the list
    in its original order.
- `report.wlo --sort count` prints what it printed before;
  `examples/rosettacode/sort_using_a_custom_comparator.wlo` and `.out` print
  `strings sample sorted Here some are be to`, one per line.
- `make test` passes.
